# Stage 1 with and without the process description

Generated by `evaluation/loanapp_p2p/scripts/make_stage1_description_ablation_report.py` from the records of `evaluation/loanapp_p2p/scripts/run_stage1_description_ablation.py`.

**Question.** Does GLASS's Stage 1 identify the expected KPIs as well without the process description? Both variants run every configuration of `setup/stage1_config.json` five times through the Step 1 batch's Stage-1 path, with the same model, temperature, number of KPIs and event-log evidence. The only difference is the process description passed to GLASS's prompt builder.

- **with_description:** the configuration's process description, as in the Step 1 batch.
- **no_description:** an empty string, passed to the existing prompt builder unchanged (GLASS v3.3 as it is, no code change). The prompt then still contains the description heading with an empty quoted block; this is what every no_description prompt contains in that place:

```text
Process Description:
""""""
```

  The rest of the prompt (system prompt, few-shot examples, goal, log and context evidence, requirements) is the same in both variants: for all 70 pairs of runs (same configuration and repetition) the system prompt, the few-shot messages and the user prompt without the description block are identical (checked when this README was written: 70 of 70 identical).

## UI keyword gate

The UI's Generate button runs `validate_generation_scope` before Stage 1. As in the Step 1 batch, the verdict is recorded per run (`scope_gate_passed`, `scope_gate_message`) but not enforced. With an empty description the gate rejects every run, so in the UI no_description would get an error and no KPIs. Messages: "The process description is too short. Please describe a real business process with activities, roles, resources, or steps.". With the description, 10 of 70 runs pass; the others fail on the goal's wording (no performance keyword), as in the Step 1 batch.

## Scoring (copied from the script header)

```
Per run, as the Step 1 batch scores it (run_stage1_batch.score, rules in that script's header):
  strict    an expected KPI is identified if its measurable_as equals (case-insensitively) the canonical
            measurable_as of a returned KPI after GLASS's normalisation (the delivered result); extras =
            returned non-null measurable_as values not expected
  lenient   an expected KPI is identified if a returned KPI satisfies its name / scope / formula rule; extras =
            returned KPIs that satisfy no expected rule
  all expected found = every expected KPI of the configuration identified (a run without an answer: none)
Per configuration and variant, over the repetitions with a delivered result:
  KPI-set Jaccard      mean over all pairs of repetitions of |A n B| / |A u B|, where a repetition's set holds
                       one key per returned KPI: its canonical measurable_as (lower case), or
                       "(<category>, <process_scope>)" when measurable_as is null (lead author's decision)
  category stability   mean over all pairs of repetitions of the multiset Jaccard of the KPI categories,
                       sum(min(count)) / sum(max(count)) (lead author's decision)
  (two empty sets: 1.0; fewer than two repetitions with a result: not computed)
Tests between the variants (two-sided):
  per configuration    Fisher exact test on runs with all expected found (5 vs 5) and on expected-KPI instances
                       identified (5 x number of expected KPIs per variant), strict and lenient
  pooled               the same Fisher tests over all runs; sign test over the configurations (ties dropped) for
                       runs with all expected found, expected KPIs identified, mean extras, mean KPIs returned,
                       KPI-set Jaccard and category stability (difference with_description - no_description)
```
