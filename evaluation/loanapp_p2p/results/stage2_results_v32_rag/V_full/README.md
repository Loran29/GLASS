## KPI validation (lead author's interpretation)

Every KPI object of category utilization passed to Stage 2 gets `target_direction = "minimize"` and the sentence "The resource is currently overloaded; bring its utilization down to a sustainable level without idling the team." appended to its description. The Stage-1 direction (maximize, in all but one case) is kept in each record as `stage1_target_direction`.

Rationale: in the G3 configurations the target pool is overloaded. Maximizing its utilization would reward overloading it further and would score the injected change's recovery (more staff) as a degradation.

GLASS evaluates the KPI with its own minimize rule on its utilization value, which is the mean of all resources' busy time over wall-clock time. The batch scores utilization KPIs with its own utilization rule on the target pool against its working time (see Scoring). GLASS's own verdicts are kept in each record (`glass_improved`).

Per-KPI inputs from the configuration (`kpi_inputs`, if set): `description_append` is appended to the KPI description and `target_threshold` is passed as `KPITarget.threshold` to the loop and the multi-seed evaluation (recorded per run as `kpi_thresholds`; GLASS's verdict per KPI as `glass_achieved`).

## Prosimos midnight end times (distance measures only)

Prosimos logs a task that ends exactly at the end of a working interval (e.g. 17:00) with an end time of 00:00 on the next day. Fixed durations proposed by patches hit that boundary regularly; the stochastic baseline durations rarely do.

CWD then compares a weekday that appears in only one log (e.g. a Saturday 00:00) and charges its maximum penalty of 23 for that weekday.

For the distance measures only, every log (baseline, initial, final, healthy) is preprocessed: an end of exactly 00:00:00 that directly follows the end of the resource's working day on the previous day is mapped back to that end. The number of mapped events is recorded per log. The raw logs are not changed.

The records hold CWD on the raw logs (`CWD_raw`) and on the mapped logs; the summary columns use the mapped values.

## How GLASS was driven (differences from the UI)

- Clarification chat: the three business-context answers (staffing, budget, immutable) as three user turns. No greeting, no assistant replies; the chatbot's readiness signal and keyword gate are not applied. GLASS summarises the chat into the prompt itself (`build_context_summary`, as after the chat in the app).
- KPI objects: first proposals come from `results/stage1_results_normalised/` (same names, measurable_as set); refinement-pilot records as configured. measurable_as is asserted non-null for every passed KPI.
- The event-log profile (app.py `extract_log_artifacts`) is passed to the loop; the UI's Generate button passes none.
- Start time from the config; the UI's loop uses 2024-01-01 09:00 UTC.
- Seeds: GLASS passes a seed to `run_prosimos_simulation`, which does not apply it. A shim seeds Python's `random` and NumPy's global RNG with that seed before each call (loop and multi-seed evaluation), so the loop's baseline and proposals use seed 42 and every model's run k uses seed 42 + k.
- Paired baseline: the baseline is simulated once per configuration for the 10 seeds (`baseline_logs/<id>/`, determinism checked by re-running the first seed); `evaluate_multi_seed` gets those runs for the baseline (served by the shim) for both the initial and the final comparison.
- KPI targets: the loop gets the UI's `_get_evaluation_targets`, the multi-seed evaluation the evaluation panel's `_get_kpi_targets_from_workspace` (with measurable_as); cost map: `_build_cost_map`.
- GLASS's Stage 2 has no process-description input; the description entered through the Stage-1 KPIs.
- cost_per_hour in the baseline resource profiles is set from business_context (the BIMP files carry none).
- Capture-only wrappers record what `validate_patch`, `apply_patch` and `build_legacy_proposal` receive and return inside GLASS (same arguments, unchanged results).
- When the best iteration is iteration 1, the final evaluation is the initial one.
- Simulated logs (`logs/`, `baseline_logs/`, `healthy_logs/`) are not in git; their SHA-256 values are in the records (and `baseline_logs/<id>/baseline.json`), and `log_archives/` holds one zip per configuration plus one per healthy model.

## Finding: GLASS utilization metric

This batch ran on a GLASS version whose `Resource Utilization` already uses each resource's available working time and is evaluated for the role the KPI names (commit 5112fbc). The earlier definition, busy time divided by the whole simulated span averaged over all resources, rose when a backlog was cleared; that made the loop discard correct fixes in batch v1. Discarded-better-initial counts below have other causes here.

The records keep both values: GLASS's in `evaluation.<phase>.kpis[*].baseline_mean / proposed_mean`, the batch's pool utilization of working time in `evaluation.<phase>.utilization_rule`. The summary CSV shows them side by side (`glass_utilization_*`, `utilization_*`).

`loop_discarded_better_initial` (summary columns; per configuration: `reps_loop_discarded_better_initial`) marks runs whose loop kept a final worse than iteration 1. Across all runs: 12 run(s); in 0 of them GLASS's utilization metric rose while the pool's utilization fell.

## Finding: constraints re-derived in every iteration

GLASS rebuilds the hard-constraints block of the patch prompt in every iteration: its summariser (`build_context_summary`, temperature 0.1) runs on the whole chat, and `inject_feedback_message` adds each iteration's simulation feedback to that chat as a user message. The feedback therefore also reaches the summariser. In 51 of 54 later iterations the block differs from iteration 1, mostly in wording.

In 4 of 124 blocks (2 of them in iteration 1), the summariser still read "+3 per internal role" as a global cap of 3 additional people across all roles, despite the rule added in `bb6cd17`.
